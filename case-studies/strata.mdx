## Context

Strata started in March 2026, born from a specific pain point: every AI coding agent I used started each session blank. Context from hours of conversation was gone by the next day. Decisions we'd made, bugs we'd fixed, architecture patterns we'd established — it all evaporated. Groundhog Day, but for coding.

I was the user, the developer, and the product manager rolled into one.

---

## Problem / Product Goal

The problem was simple and maddening: **AI agents have no persistent memory.**

The existing approaches all had the same flaw: they tried to be smart all the time.

- **Infinite context windows** shove everything into the prompt. Reasoning degrades, tokens burn.
- **Vector databases** dump everything into embeddings and hope the similarity search surfaces what matters. Works for facts, fails for nuance.
- **mem0, LangMem, OpenClaw** use LLMs to constantly monitor and reorganize memory. Every query triggers a check, every operation runs a janitor loop. Great in demos, costly at scale.

I wanted something that would let an agent remember last week's architecture decision without paying GPT-4o to read a 10KB file and decide whether it was still relevant. The goal was: **a memory system that costs nothing for routine operations, only spending money when intelligence is actually required.**

---

## Thought Process

My first attempt was a blog post. I sketched out a two-component system: a tiered memory store (Strata) plus a relational "agent-db" built on Postgres with pgvector. The idea was that Stratum 1 would be active files, Stratum 2 would be a Postgres-backed relational store with vector search, and Stratum 3 would be a compressed archive.

I started building it. Wrote the three-tier storage layer, the janitor lifecycle logic, the CLI, the MCP server — about 11 commits in 3 days. And then I hit a wall.

The Postgres layer was going to add:

- A hard dependency (must install and run Postgres)
- Embedding costs for every file that moved between strata
- A vector similarity query for every search
- Schema management overhead for a feature I wasn't sure anyone needed

I sat with this for two days. I had built a perfectly good three-tier system, but Stratum 2 was a third-party dependency that made the whole thing less useful, not more.

**The breakthrough came when I asked myself: what does the Janitor actually need?**

Check a timestamp. Compare it to a threshold. Maybe copy a file from one directory to another. That's the whole job. The LLM in the lifecycle loop was cargo-cult intelligence — I was adding smarts where reliability would do.

I removed the Postgres layer. Made Stratum 2 a filesystem directory. Changed the eviction trigger from "LLM decides this is stale" to "file hasn't been accessed in 90 days." Cut the entire embedding pipeline.

The Janitor went from "call an API and parse JSON" to "check a timestamp and maybe copy a file." The tests got faster. The install went from "pip install && docker-compose up" to "pip install && strata init." No dependencies, no ongoing costs, and the routine work runs without a single LLM call.

Then I realized the Shadow Index — a simple SQLite FTS5 keyword index for archived files — was actually the killer feature. Every competing system either grows forever (mem0 keeps everything in the vector DB, costs go up linearly) or deletes permanently (old data is just gone). The Shadow Index stores only keywords, a 200-character preview, and a file path. A million entries cost less than a megabyte. When a search finds a match, the file gets rehydrated back to active automatically. You never truly lose anything — it just gets put away until you need it again.

## Solution

**Strata is a three-tier filesystem memory system for AI agents, powered by an algorithmic janitor.**

### Tier 1: Active

Plain markdown files in `active/`. The agent reads and writes directly. An auto-generated `index.md` lists every file with its first heading as description — no vector database needed. Latency: ~1ms. Cost: zero.

### Tier 2: Cooled

Files move here when they exceed configurable age thresholds (14 days for projects, 60 for entities, 7 for GTD). Still plain markdown, just in a different directory. Read-only via search. If a cooled file gets accessed ≥3 times, it's automatically promoted back to active. **Bidirectional lifecycle.**

### Tier 3: Archive

Files not accessed for 90 days get archived. Full content saved as JSON. A Shadow Index (SQLite FTS5) keeps everything keyword-searchable — no vectors, no embeddings. When a search hits the archive, the file is automatically rehydrated back to active.

### The Janitor

The only process that moves data between tiers. Four operations — migrate, evict, promote, rehydrate — all driven by file age and access count. Zero LLM calls. The daemon runs on a 15-minute interval, first cycle always a dry run.

### Integration with Pi (coding agent)

A pi extension hook saves every conversation transcript automatically. An optional background distiller runs a cheap LLM (GPT-4o-mini, ~$0.01 per cycle) to extract facts. An MCP server exposes Strata tools over JSON-RPC 2.0. A skill install command supports 55+ agent formats.

## Takeaways

**The Janitor doesn't need to be smart.** This was the single most important decision in the project. I almost built a system where every lifecycle operation required an LLM call. Removing that dependency made the system simpler, faster, cheaper, and more reliable. The lesson was straightforward: filesystem operations are simple, and that's a feature, not a limitation.

**The Shadow Index was an afterthought that made the whole thing special.** I added it for completeness. Competitors (mem0, QMD, OpenClaw) can't replicate it — they either grow forever or delete permanently. Sometimes the features that matter most come from what you build on the side, not what you planned.

**Path matching is harder than it looks.** The config system needs to apply different decay rates for different content types — "pi/conversations" should decay faster than "pi/entities." Getting the multi-component path prefix matching right (with edge cases like "pi/conversations/longer/path" correctly matching "pi/conversations") took three attempts. The solution was checking progressively longer path prefixes in a loop — simple, correct, testable.

**Write-time simplicity, pay at read time.** The distiller writes append-only facts without dedup. Multiple facts about the same entity can coexist. The agent reconciles them by timestamp at read time. This sounds wasteful, but keeping the write path simple prevented a cascade of complexity (merge logic, conflict resolution, versioning) that would never have been worth it for a single-user tool.

**Forgetting is the feature.** I started with "how do I store everything?" The right question was "how do I store each memory at the fidelity it deserves?" Information decays on purpose. That's what makes memory useful.
